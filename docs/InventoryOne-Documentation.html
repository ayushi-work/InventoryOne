InventoryOne: Broker Web App

Project Description

The InventoryOne: Broker Web App is a real-estate platform that allows registered brokers to register and log in via OTP with KYC verification, view active projects with live colour-coded plot availability, view plot details, register customers, raise booking requests, track commissions, download documents, and stay updated via notifications.

Company administrators can manage projects, plot inventory, and broker bookings, and approve or reject booking requests.

The project will be developed using the Agile methodology, with development divided into short sprints for continuous development, testing, and improvement.

Running the Application

Prerequisites

  • Python 3.11 – 3.13
  • Node.js 20+
  • PostgreSQL 14+

1. Backend (Django + DRF)

cd src/backend

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# Create the database (once)
createdb inventoryone

# Apply migrations and load demo data
python manage.py migrate
python manage.py seed_demo

# Start the API on http://127.0.0.1:8000
# Daphne serves both HTTP and the live-inventory WebSocket
python -m daphne -b 127.0.0.1 -p 8000 inventoryone.asgi:application

Optional services (the app degrades gracefully without them):

# Redis - powers live inventory updates and Celery background jobs
redis-server

# Celery worker - demand letters and notification fan-out
celery -A inventoryone worker -l info

2. Frontend (Next.js)

cd src/frontend

npm install
npm run dev      # http://127.0.0.1:3000

The frontend talks to the API at http://127.0.0.1:8000 by default. Override it with NEXT_PUBLIC_API_URL (and NEXT_PUBLIC_WS_URL for the WebSocket) if the API runs elsewhere.

3. Docker (full stack)

cp .env.example .env   # then fill in the values
docker compose up --build

Brings up PostgreSQL, Redis, the Django/Daphne backend, a Celery worker and the Next.js frontend.

  • Provide downloadable documents and real-time notifications.
  • Reduce manual coordination, waiting time and improve booking transparency.

The InventoryOne: Broker Web App supports broker registration and KYC, project and plot inventory viewing, customer registration, booking requests with company approval, commission management, document downloads, notifications and support tickets. Customer-facing portals, loan processing, account creation for customers and native mobile applications are outside the scope of this project.

2. Overall Description

2.1 Product Perspective

InventoryOne is a new, self-contained web application built as a client–server system:

  • Frontend: Next.js + TypeScript single-page web application.
  • Backend: Django REST Framework REST API.
  • Database: PostgreSQL accessed through the Django ORM.
  • Real-time: Django Channels + Redis for live availability updates.
  • Supporting services: Firebase Auth/FCM, AWS S3 (documents), Google Maps API, Celery + Redis (background jobs), Django Admin (administration).

The system interacts with external services (OTP/SMS gateway, Firebase, S3, Maps) but the software running on those services is not part of this specification.

2.2 Product Functions

  1. Register and authenticate brokers using OTP.
  2. Capture and validate broker KYC and bank details.
  3. Maintain projects and plot inventory.
  4. Display live, colour-coded plot availability.
  5. Show plot details and pricing.
  6. Register customers against a broker.
  7. Raise booking requests (token amount + payment mode).
  8. Approve or reject booking requests (administrator).
  9. Compute and track commissions with TDS.
  10. Download documents (price lists, forms).
  11. Send notifications for projects, schemes and booking updates.
  12. Raise support tickets and contact the relationship manager.

User Class Description Technical Skill Frequency of Use

  • Server: Linux-based cloud host (AWS / Render / Railway).
  • Database: PostgreSQL 14 or later.

2.5 Design and Implementation Constraints

  • Frontend must use Next.js + TypeScript; backend must use Django + DRF.
  • Data must be stored in PostgreSQL and accessed through the Django ORM.
  • Passwords and OTPs must never be stored in plain text in logs.

  • The system must follow responsive web design for desktop and mobile browsers.

2.6 Assumptions and Dependencies

  • Brokers possess a valid mobile number and e-mail for OTP delivery.
  • The company maintains accurate project and plot master data.
  • Third-party OTP, maps, and messaging services remain available.
  • Payment gateway selection is pending and does not block the booking workflow.

Introduction

A Use Case Diagram establishes the capability of the system as a whole, showing who uses the system and what the system does without revealing its internal structure. It consists of actors, use cases, the system boundary, and relationships. Each use case is a sequence of related transactions (a dialogue) between an actor and the system.

1. Conceptual Description

1.1 Components of a Use Case Diagram

Component Description
Actor Someone or something that interacts with the system
Use Case A pattern of behaviour the system exhibits
System Boundary A rectangle separating internal (system) from external (actors)
Relationship Association (communicates), Include (<<include>>), Extend (<<extend>>)

1.2 Categories of Actors

Introduction

Software design is the bridge between software requirements and implementation. After completing the Software Requirement Specification (SRS), developers transform user requirements into a structured technical solution. A good design simplifies implementation, improves maintainability, reduces development cost and facilitates future enhancements. The design phase determines the architecture, modules, interfaces, data structures and interactions among system components.

Conceptual Background

Characteristics of Good Software Design

A good software design should be modular, reusable, scalable, secure, efficient, reliable, maintainable and easy to test. It should minimise complexity while maximising readability and extensibility.

Modularization

Modularization divides a large software system into smaller independent modules. Each module performs a single well-defined responsibility. For the InventoryOne Broker Web App, Authentication, KYC, Project & Inventory, Customer, Booking, Commission, Notification, Document and Support are separate modules.

Abstraction

Abstraction focuses on essential behaviour while hiding implementation details. A broker interacts only with services such as View Live Plot Availability or Raise Booking Request without knowing how inventory status, database persistence or notification delivery are internally executed.

Information Hiding

Each module hides its internal implementation and exposes only necessary interfaces. For example, the OTP generation and verification logic is hidden inside the Authentication module, and commission/TDS calculation is hidden inside the Commission module.

Coupling

Coupling measures interdependence between modules. Low coupling is desirable because changes in one module should have minimal impact on others.

Cohesion

Cohesion measures how closely related the responsibilities of a module are. Functional cohesion, where a module performs exactly one task, is considered the highest quality.

Function-Oriented Design

The software is decomposed into functions. Data flows between functions and each function performs a specific operation.

Object-Oriented Design

The system is modelled using classes and objects that encapsulate data and behaviour. In the InventoryOne Broker Web App, classes such as Broker, Project, Plot, Customer, Booking and Commission collaborate through object interactions.

Top-Down Design

Development begins with the overall system and progressively decomposes it into smaller modules.

Bottom-Up Design

Low-level reusable components are developed first and then integrated into higher-level subsystems.
